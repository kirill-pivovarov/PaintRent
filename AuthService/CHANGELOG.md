[2.0.0] — Модуль безопасности и аутентификации
Краткое резюме изменений
Разработан и интегрирован сервис аутентификации (AuthService), отвечающий за регистрацию пользователей, выдачу токенов доступа, безопасное управление сессиями и мониторинг компрометации учетных записей.
1. Архитектура аутентификации: зачем нужны два токена?
В сервисе реализована гибридная модель Stateless Access (JWT) + Stateful Refresh (База данных).
Вместо использования одного долгоживущего токена система разделяет полномочия на два независимых ключа:
1.1. Access Token (JWT — короткоживущий токен доступа)
Срок жизни: 15 минут.
Где хранится: в оперативной памяти клиента (не сохраняется в базе данных).
Зачем нужен:
Передаётся в заголовке Authorization: Bearer <token> при каждом запросе к бизнес-API (каталог картин, заказы, корзина).
Преимущество:
Основной сервис (GatewayService) проверяет подпись токена локально в памяти с помощью криптографического секрета, не делая сетевых запросов к AuthService и не нагружая базу данных лишними операциями чтения.
Безопасность:
Если токен будет перехвачен злоумышленником, «окно уязвимости» ограничено 15 минутами, после чего токен автоматически становится недействительным.
1.2. Refresh Token (Opaque Token — долгоживущий токен обновления)
Срок жизни: 30 дней (скользящий срок).
Где хранится: у клиента — в защищенном хранилище; на сервере — в таблице refresh_tokens базы данных PostgreSQL исключительно в виде необратимого криптографического хэша SHA-256.
Зачем нужен:
Используется только для одного действия — обращения к эндпоинту POST /api/v1/auth/refresh для получения нового Access-токена, когда старый истек.
Преимущество:
Позволяет управлять жизненным циклом сессии: реализовывать принудительный логаут, отзыв прав администратором или завершение сеансов на конкретных устройствах.
2. Мультисессионность и концепция session_id
Чтобы пользователь мог одновременно работать с нескольких устройств (например, с рабочего ноутбука и личного смартфона), введена сущность session_id (Семейство токенов / Token Family):
При входе (/login) или регистрации (/signup):
Генерируется уникальный session_id = uuid.uuid4(). Это создает новую независимую ветку сессии.
При обновлении токена (/refresh):
Новый токен наследует session_id своего предшественника, сохраняя целостность цепочки конкретного устройства.
Изоляция:
Ротация или завершение сессии на смартфоне никак не влияет на активную сессию на ноутбуке.
3. Сценарий защиты от перехвата и кражи токенов (Reuse Detection)
Для предотвращения атак типа Man-in-the-Middle (MitM) и кражи сессий реализован механизм ротации токенов с обнаружением повторного использования (Refresh Token Rotation & Reuse Detection) в соответствии со спецификацией OAuth 2.0 Security Best Current Practice.
3.1. Штатная ротация (Happy Path):
Каждый Refresh-токен является строго одноразовым:
При вызове POST /api/v1/auth/refresh сервер переводит использованный токен в статус is_revoked = True.
Взамен генерируется абсолютно новый Refresh-токен в рамках того же session_id, а срок действия сессии продлевается на 30 дней от текущего момента.
Клиент перезаписывает токен у себя в памяти и стирает старый.
3.2. Сценарий перехвата злоумышленником (Security Alarm):
Перехват: Злоумышленник перехватывает активный Refresh_Token_1 легитимного пользователя.
Штатный шаг: Пользователь ничего не подозревает, его клиент отправляет Refresh_Token_1 на обновление. Сервер гасит его (is_revoked = True) и выдает пользователю Refresh_Token_2.
Атака: Спустя время злоумышленник пытается отправить украденный Refresh_Token_1 на эндпоинт /refresh.
Реакция сервера:
Сервер находит запись в БД и видит: is_revoked == True (токен уже погашен).
Сервер запрашивает все токены этой сессии (session_id) и обнаруживает, что в сессии уже существует более свежий активный токен (Refresh_Token_2).
Вывод системы: легитимный клиент никогда не отправляет старый токен повторно — произошла компрометация учетных данных!
Действие системы безопасности:
Сервер мгновенно аннулирует (is_revoked = True) абсолютно все токены и сессии данного пользователя во всей базе данных.
Транзакция принудительно фиксируется в базе (await db.commit()).
Сервер возвращает статус 401 Unauthorized с деталями о компрометации сессии.
В результате доступ блокируется и для хакера, и для скомпрометированного устройства, а пользователю потребуется выполнить повторный вход по паролю.
4. Ленивая очистка устаревших данных (Lazy Cleanup)
Чтобы таблица refresh_tokens не разрасталась бесконечным количеством использованных записей, при каждом успешном вызове эндпоинта /refresh выполняется автоматическая очистка:
Удаляются токены, чей срок жизни (expires_at) окончательно истек.
Удаляются старые отозванные токены, созданные ранее заданного окна хранения (refresh_token_ttl_days * 3).
Это исключает необходимость запуска внешних фоновых демонов (cron/celery) на данном этапе проекта и сохраняет высокую производительность запросов к БД.
5. Структура API-эндпоинтов AuthService
POST /api/v1/auth/signup — регистрация новой учетной записи, генерация первичного session_id, выпуск пары { access_token, refresh_token }. Возвращает 201 Created (или 409 Conflict, если email занят).
POST /api/v1/auth/login — аутентификация по email и паролю с использованием безопасного алгоритма сверки хэшей. Инициализация новой независимой сессии устройства.
POST /api/v1/auth/refresh — ротация токенов, валидация статуса сессии, применение алгоритма Reuse Detection и фоновая очистка устаревших записей.
