# PaintRent

# Задание на лабораторную работу

## 1. Выбрать предметную область. Сформулировать бизнес-цель приложения.

**Предметная область:** сервис по аренде картин для физлиц и бизнеса.

**Бизнес-цель:** предоставить клиентам удобный сервис, где за короткое время можно выбрать и приобрести/арендовать интересующую картину, а партнёрам — быстро и удобно сдавать свои работы в аренду и продавать их.

## 2. Описать функционал приложения. Описать сценарий использования

### Роли пользователей

| Роль | Описание |
|---|---|
| **Клиент** | Физическое лицо или представитель бизнеса, который просматривает каталог, арендует или покупает картины |
| **Партнёр** | Владелец картин, который выставляет их в каталог, подтверждает или отклоняет запросы |
| **Администратор** | Управляет пользователями и контролирует заказы в системе |

## 3. Архитектура приложения

- **Main API Service.** RESTful. Входная точка в систему. В нём содержится основная бизнес-логика. Принимает внешние HTTP-запросы клиентов (FastAPI), валидирует данные с помощью Pydantic, авторизирует пользователей с помощью JWT-токенов, координирует работу других микросервисов.
- **DB Service & Database.** Слой хранения данных с помощью PostgreSQL и работа с ними через SQLAlchemy и работы с ними (CRUD).
- **Auth Service.** Сервис аутентифицирует пользователей и выдаёт им JWT-токены для дальнейшей авторизации.
- **gRPC recommendation service.** Создаёт список рекомендованных картин для пользователя.
- **RabbitMQ Server.** Асинхронный брокер сообщений для обмена событиями между компонентами.
- **Notification Service.** Подписывается на очередь RabbitMQ, формирует уведомления и отправляет их через WebSocket.

## 4. Логическая и физическая структура базы данных

Есть три глобальных сущности: **User**, **Painting**, **Order** (User 1:m Painting, User 1:m Order, Order m:m Painting).

У сущности **User** есть несколько ролей: **client**, **partner**, **admin**. Для этих ролей в базе данных создаются отдельные профили.

Для реализации связи многие ко многим между заказами и картинами создана промежуточная таблица **Order_item**. Один заказ состоит из нескольких order_item-ов, что позволяет за один заказ купить и/или арендовать несколько картин.

У заказа и у элемента заказа есть статус. Статус может принимать одно из 4 значений: **создан**, **подтверждён**, **оплачен** и **отменён**.

### Статусы элементов заказа (order_item)

- При создании элемента заказа он получает статус **CREATED**, при этом партнёру отправляется уведомление на подтверждение элемента заказа.
- Партнёр может как подтвердить элемент заказа, тогда он получает статус **CONFIRMED**, так и отменить, в этом случае элемент заказа получает статус **CANCELED**.
- Если партнёр подтвердил элемент заказа, то клиенту остаётся лишь его оплатить, тогда элемент заказа получит статус **PAID** (этот статус считается финальным).
- При этом любой из акторов может отменить выполнение элемента заказа на любой стадии.

### Статусы заказа (Order)

Статусы заказа зависят от статусов элементов заказа, в него входящих:

- При создании заказа он получает статус **CREATED**.
- При подтверждении всеми партнёрами всех элементов заказа, входящих в данный заказ, он получает статус **CONFIRMED**.
- Если один из элементов заказа был отменён партнёром, то этот элемент заказа удаляется из общего заказа.
- После оплаты клиентом заказа, сам заказ и все его элементы получают статус **PAID**.
- Если все элементы заказа были отменены партнёрами или клиент отменил заказ целиком, то он получает статус **CANCELED**.
